# RFC-014: Move ledger-svc behind PgBouncer

**Status:** accepted · **Author:** Rohan Mehta · **Reviewers:** Ananya Iyer, Farhan Qureshi, Sara Kim · **Rollout:** Thu 3 Sep 2026, 14:00 IST

## Problem
Each ledger-svc pod holds a HikariCP pool of 20 real Postgres connections. Scaling ledger-svc scales connections linearly, and bursts (INC-4127, INC-4165) pin the pool and pile up server connections.

## Proposal
- Deploy `pgbouncer-ledger` (PgBouncer 1.23, 2 replicas) in front of postgres-ledger with `pool_mode=transaction`, `default_pool_size=20`, `max_db_connections=40`, `max_client_conn=2000`.
- Point ledger-svc at pgbouncer-ledger and shrink `spring.datasource.hikari.maximum-pool-size` from 20 to 10 per pod: client connections to PgBouncer are cheap, server connections are what we protect.
- Disable server-side prepared statements in the JDBC URL (`prepareThreshold=0`), as transaction pooling requires.

## What changes for on-call
- Pool pressure now shows up in PgBouncer: `pgbouncer_cl_waiting` (clients waiting for a server connection) and `query_wait_timeout` errors in the pgbouncer-ledger logs.
- The HikariCP pool is no longer the bottleneck. Raising `maximum-pool-size` will not help; the knob is PgBouncer's `default_pool_size` (and `max_db_connections`), owned by Data Platform.
- Long transactions still hold server connections, so a change that lengthens transactions still needs rolling back.
